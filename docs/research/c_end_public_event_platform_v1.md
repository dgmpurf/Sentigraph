# C端公众事件平台 v1 产品方案

## 1) 一句话定位

C端“公共事件舆情生态”作为 Sentigraph 的公众展示层，面向普通用户提供：

- 可浏览的公共事件分析看板
- 事件请求/投票入口
- 典型事件的公开沙盒页
- 清晰的样本边界和可信声明

B端版本仍是深度分析与咨询化服务入口。  
C端不承诺“官方级舆情真相”，不做“全网自动抓取与实时全平台覆盖”承诺，而是通过公开样本与手工合规证据让用户理解分析方法与边界。

## 2) 为什么先做 C 端

1. 先建立可见性：让外部用户快速理解产品价值，而不是只在研发文档里停留。  
2. 先建立理解链路：公众可见页与示例事件可降低认知门槛，便于后续客户沟通。  
3. 形成需求线索：通过请求/投票让平台优先处理高关注事件。  
4. B端增长支撑：C端作为传播和教育层，B端保持付费深度分析与合规交付。  
5. 适配当前能力：在保留现有边界的前提下，先交付可演示的最小闭环。

## 3) 产品边界（必须写在页面上）

- 不是全网爬虫产品，不做任何登录态抓取。  
- 不是全平台全域覆盖。  
- 不是官方认证结果，不代表“官方核验”。  
- 不是因果推断（非因果证明）。  
- 不触发真实平台动作（不发布、不删帖、不介入平台运营）。  
- 不用于隐蔽水军/导流/控评。  
- 公开页面必须标注样本来源状态与覆盖限制。  
- 有赞助/请求分析时必须明确标注“赞助/请求来源”而非自然热度。  

## 4) C端信息架构（v1）

### A. Public Event Plaza（事件广场）
- 汇总公开事件卡片与基础状态  
- 提供“查看分析 / 请求分析 / 投票”动作

### B. Public Event Detail（事件详情）
- 事件叙事摘要、时间线、样本与覆盖说明  
- 对应沙盒的可见入口（可展开）  

### C. Opinion Ecosystem Sandbox（生态沙盒嵌入）
- 嵌入式展示，默认关闭高级参数  
- 显示核心可视化：EchoBox、PeopleCluster、InfluenceCore  

### D. Event Request/Vote（事件请求与投票）
- 提交事件标题与公开链接、请求理由（非强制登录）  
- 收藏与投票按钮  

### E. About Data & Limitations（数据与限制说明）
- 样本类型说明、覆盖范围、可信度标签解释  

### F. Contact / B-end inquiry（联系入口）
- B端咨询入口（如“企业咨询”“试用申请”）  
- 引导到私域沟通渠道

## 5) 事件广场 v1 设计

单卡片字段建议：

- 事件标题（必要）
- 事件类型：游戏 / 动漫 / 品牌 / 创作者 / 社区 / 产品
- 事件状态：
  - `pending_request`
  - `sample_available`
  - `sandbox_available`
  - `archived`
- 热度指标（用户活跃度或请求量）
- 争议度（人工标注或公开讨论强度）
- 失控风险（Breakout risk）
- 样本状态（selected public sample / synthetic demo / pending analysis）
- 倾向分布：支持 / 中立 / 反对
- CTA：
  - 查看分析
  - 请求分析
  - 参与投票

边界说明：
- 禁止“自然热榜”措辞，避免未验证排序承诺。
- 热度来源需说明是“用户提交/请求与样本可见度驱动”，非平台级完整热度。

## 6) 事件详情 v1 结构（v1）

以 Helldivers PSN 为首个公开样本页：

- 事件摘要（1-3 句）
- 时间线（若干关键时间点）
- 样本状态卡（必须显示）
- Evidence 与来源覆盖说明
- InfluenceCore 列表（核心叙事/官方信息/媒体/梗来源）
- EchoBox 总结（争议与讨论特征）
- PeopleCluster 分布（匿名群组维度）
- Opinion Ecosystem Sandbox（交互卡）
- ResponseTempo 变化说明（回应节奏、迟缓回应说明）
- ReputationMemory / 长尾风险（若可用）
- Mapping contract 与校验说明（不涉敏感、不泄露）
- 页面不证明：
  - 官方性
  - 全网性
  - 因果因果
  - 真实个人画像

## 7) 沙盒在 C端角色

- C端沙盒主打“可读可看”：以视觉解释事件演化而非替代人工决策。  
- EchoBox 描述为“受限讨论舱”，强调语境与话题聚合。  
- PeopleCluster 球体为匿名群组/讨论群体，不代表真实用户个体。  
- InfluenceCore 为叙事/媒体/官方/梗内容核心，不是人群小球。  
- 场景控件保持简单：
  - 自然演化
  - 官方澄清
  - FAQ/长文解释
  - 第三方说明
  - 社区解构
  - 延迟回应
  - 无回应

说明策略：
- 不在 C 端强调模型术语，尽量用“讨论演化”“舆情走向”等通俗语。

## 8) 事件请求/投票机制

提交项建议：

- 事件标题（必填）
- 公开链接（选填）
- 请求理由（选填）

机制规则：
- 支持“用户主动请求”与“事件提名”。  
- 赞助/请求分析入口必须显式标签，如“赞助/邀请分析”。  
- 投票计数与自然热度不混合展示。  
- 禁止“带节奏”“煽动性”文案与暗箱操作。  
- 不做“虚假热度制造”；不展示未验证真实影响统计。

## 9) 数据状态与标签

状态标签定义（面向公开页）：

- `selected public sample`
  - 含义：已人工挑选并用于公开展示的样本
  - 不含义：非全量抓取结果、非官方确认
  - 可公开：是（需边界说明）

- `synthetic demo`
  - 含义：用于演示场景的模拟输入或整理样本
  - 不含义：非真实事件全量输入
  - 可公开：是（显著提示）

- `pending analysis`
  - 含义：已入列，未完成完整分析
  - 不含义：未公开可引用的最终结论
  - 可公开：是（说明待完成）

- `user-requested`
  - 含义：由用户提名/请求
  - 不含义：天然舆情热点排名
  - 可公开：是（附请求来源）

- `sponsored analysis`
  - 含义：明确付费或委托请求
  - 不含义：自然舆情自然增长
  - 可公开：是（独立于自然热度显示）

- `external evidence package`
  - 含义：来自外部合法文件/样本包
  - 不含义：已官方核验
  - 可公开：是（限制字段展示）

- `vendor sample`
  - 含义：第三方样本数据包映射
  - 不含义：官方授权等价
  - 可公开：是（在合规前提）

- `official API sample`
  - 含义：具备官方授权采集凭据
  - 不含义：平台级完整覆盖
  - 可公开：是（仍需说明覆盖范围）

- `mock/static`
  - 含义：演示/离线本地样本
  - 不含义：实时平台状态
  - 可公开：是（默认在首页置顶强调）

## 10) C端 MVP 第一次范围

v1 建议上线：

- 事件广场（3 个卡片）：例如 Helldivers PSN + 2 个静态样本事件
- Helldivers PSN 详情页（样本公开页面）
- 嵌入式沙盒展示（无需后端即显示）
- 事件请求与投票表单（静态提交流程）
- B端咨询 CTA

v1 不做项：

- v1 不做用户账号体系
- v1 不做公开评论系统
- v1 不做实时抓取
- v1 不做真实支付/赞助结算（待后续明确）

## 11) 增长闭环（v1）

1. 用户浏览公开事件  
2. 用户提交请求/投票  
3. 高兴趣事件进入候选池  
4. 被选中事件进入公开样本分析页  
5. 内容可被转发形成自然传播  
6. 同类机构/品牌的 B 端团队产生咨询与跟进

## 12) 与 B端的桥接

- C 端：公共认知入口，提供样本化展示与基础理解。  
- B 端：私域深度分析服务（更完整数据、人工复核、私有语境、场景对比报告）。  
- 转化方式：
  - 在事件页加入“需深度决策咨询请联系 B端团队”按钮
  - 明确说明 C 端仅供公开信息参考，B端可提供更完整工作流

## 13) 投资人/客户叙事

一句话：从“仅工具页面”走向“可共享可复核的舆情理解平台”。

- 痛点：复杂舆情信息难以被快速理解，企业和公众均缺少透明入口。  
- C端价值：
  - 用户能快速看到事件如何演化、什么是样本、边界在哪里  
  - 企业可通过公开样本建立专业形象  
  - 投资人看到的是“可交付、可解释、可扩展”的产品路线  
- 不同于传统舆情面板：强调“证据链边界 + 审核状态 + 沙盒可视化解释”，不是仅情绪分布图。  
- 不强调“我们是爬虫平台”，不强调“官方全网监测”。

## 14) 后续可追踪指标（先定义不立即实现）

- 事件页访问量
- 请求数与投票数
- 分享次数
- 沙盒停留时长
- 场景切换行为（不同响应策略点击率）
- B端咨询点击率
- 公域转私域率（从事件页到咨询）
- 重复访问率

## 15) 风险与禁忌清单

- 风险：公众误读“抽样样本为全局事实”  
  - 应对：页面统一展示样本边界与限制
- 风险：被解读为“攻击个人/群体”  
  - 应对：清晰去标识个人、群体匿名展示
- 风险：赞助内容误认为自然舆情  
  - 应对：赞助/请求必须显著标签
- 风险：模型稳定性过度宣称  
  - 应对：只描述已支持的信息，不做因果结论
- 风险：页面术语过重导致认知门槛高  
  - 应对：保留中文名词解释，不使用过多黑箱术语
- 风险：合规审核不足  
  - 应对：将法务、ICP/网安备案视为独立里程碑，不纳入本 spec 即时承诺
