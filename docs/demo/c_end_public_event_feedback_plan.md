# C 端公共事件平台反馈计划（v1）

## 1. 为什么现在要做用户反馈

C 端演示版本已经具备事件入口、样本详情、生态可视化、时间线预设、请求/投票 mock 与 B 端咨询入口。

但当前最关键风险是：

- 用户是否理解“不是全网真值”边界
- 用户是否误把 mock 行为理解为真实热度
- 用户是否能区分 PeopleCluster 与 InfluenceCore
- 是否能从视觉结构中获得“可复用的事件理解能力”

因此需要第一轮用户反馈，把“可理解性 / 信任度 / 分享意愿”与“商业化转化兴趣”转为可量化数据。

## 2. 先问哪些人

1. 普通游戏玩家
2. ACG 社区用户
3. 内容创作者 / UP 主
4. MCN / 公关 / 品牌 / 社区运营
5. 游戏社区运营
6. 技术 / 产品朋友

## 3. 反馈场次设计

### 3.1 5 分钟速览
- 5 分钟内完成：
  - 事件广场
  - Helldivers 详情页
  - 沙盒 V2 首屏
  - 只看边界文案
- 输出：第一印象 + 是否理解边界

### 3.2 15 分钟引导演示
- 按标准路径完整走一遍 3 分钟脚本
- 重点观察：
  - 页面是否容易找
  - 是否能理解交互意义
  - 是否误解数据真实性

### 3.3 30 分钟专家访谈
- 适用于品牌方、MCN、公关、技术评审角色
- 深入讨论：
  - 哪些页面有决策价值
  - 哪些指标可公开展示
  - 如何避免不合规认知偏差
  - 后续最想要的最小改进

## 4. 访谈问题

- 你是否理解这个产品在做什么？
- 哪个页面最有帮助？
- 你是否觉得 Sandbox v2 更容易理解事件？
- 你是否信任样本限制与边界文本？
- 哪一处你觉得最困惑？
- 你愿意再请求一个其他事件分析吗？
- 你愿意分享事件页给他人吗？
- 如果你是品牌/MCN/创作者，这能支持你的决策吗？

## 5. 评分模板（每项 1–5 分）

- 事件理解清晰度（Clarity）
- 页面可用性（Usefulness）
- 对样本边界的信任（Trust）
- 愿意分享意愿（Share Willingness）
- 继续请求其他事件意愿（Replay/Request）
- B 端商业兴趣（B-end Interest）

建议记录一个综合意见：

- 明确建议项（最多 3 条）
- 明确不能接受项（最多 3 条）

## 6. 红线识别（Red Flags）

- 用户认为是“全网真相”
- 用户认为投票数为真实热度
- 用户认为系统在“操控舆论”或“强制导向”
- 用户无法区分 PeopleCluster 与 InfluenceCore
- 用户忽略边界提示并继续误解
- 用户要求官方 API 结果却未确认合规审批

发现红线需立即加入风险说明和引导文案修订。

## 7. 安全反馈流程

- 只记录问题类别、反馈结论与评分
- 不收集实名个人身份、账号密码、敏感隐私信息
- 不进行平台账号登录绑定
- 不采集后台私有平台数据
- 不默认承诺：
  - 全网覆盖
  - 官方背书
  - 因果结论
  - 真实投票热度

## 8. 反馈数据落地

### 数据字段建议（人工记录表）

- 受访者角色
- 场次类型（5/15/30 分钟）
- 5 项评分
- 红线触发（是/否）
- 关键建议
- 关键误解点
- 负责人备注

### 复盘动作

- 一周内形成一版反馈修订清单
- 优先修复边界误解和文案歧义项
- 每次演示前更新“请勿误解清单”

## 9. 必须坚持的安全说明（每场演示前确认）

- frontend-only 本地原型
- selected public sample
- request/vote 仅为 mock
- not full-web / not full-platform / not full-thread coverage
- not official verification
- not causal proof
- no real platform action
- no real API and no real LLM
- PeopleCluster 是匿名群体/群簇，不是真实个人
- InfluenceCore 是内容/叙事/官方/媒体/梗核核心节点
- 不做隐性“买榜”或真实热度承诺
